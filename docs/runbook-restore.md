# Восстановление сервера с нуля

Что делать, если сервер нужно поднять заново: умер диск, переустановлена система, переезд на другое
железо. Сервер описан кодом в [`ansible/`](../ansible/), поэтому восстановление — это чистый Debian,
несколько ручных шагов и один запуск плейбука. Сценарий проверен на чистой ВМ
(см. [«Как проверялось»](#как-проверялось)).

**Время восстановления (RTO): до часа**, из них около 20 минут — установка Debian, около 35 — первый
прогон плейбука. Это верхняя оценка: замер сделан на ВМ с эмуляцией x86_64, на настоящем железе быстрее.

**Что теряется:** история метрик Prometheus (хранится 15 дней) и состояние Alertmanager (тишины).
Всё остальное либо создаётся плейбуком, либо хранится вне сервера (таблица ниже).

## 1. Что должно быть вне сервера

| Что | Где хранится | Без этого |
|---|---|---|
| Репозиторий | GitHub и два зеркала (GitLab, GitVerse) | нечего запускать |
| Файл с секретами (ansible-vault) | на управляющей машине, вне клона; образец — [`vault.example.yml`](../ansible/vault.example.yml) | роли `proxy` и `monitoring` не запустятся |
| Пароль от файла с секретами | менеджер паролей | файл не расшифровать |
| SSH-ключ управляющей машины | управляющая машина | вход на сервер только по ключу |
| Доступ к панели управления VPN | учётная запись владельца | служебные сайты не откроются |
| Настройки вне Ansible: DNS домашней сети, другие сервисы на сервере | приватный репозиторий владельца | имена `*.home.arpa` не разрешатся |

В файле с секретами — пароль администратора Grafana, адреса для уведомлений и **корень центра
сертификации** обратного прокси (сертификат и ключ). Корень хранится там, а не генерируется на сервере:
восстановленный сервер выдаёт сертификаты, которым устройства уже доверяют, и корневой сертификат
не нужно заново ставить на телефоны и ноутбуки.

Чего **не** нужно сохранять: тома Docker. Сертификаты сайтов и промежуточный сертификат Caddy выпустит
заново от того же корня, дашборды и источник данных Grafana лежат в репозитории, правила алертов — тоже.

## 2. Требования

- **Железо:** x86_64. Образы в GHCR публикуются только для `linux/amd64`, плейбук проверяет архитектуру
  первым шагом. 4 ГБ памяти и 20 ГБ диска достаточно (на стенде хватило с запасом).
- **Система:** Debian 13 (trixie), установка с образа netinst.
- **Сеть:** первый прогон скачивает около 2 ГБ (пакеты, cosign — 145 МБ, образы). Серверу должны быть
  доступны:

  | Адрес | Зачем |
  |---|---|
  | `deb.debian.org`, `security.debian.org` | пакеты Debian |
  | `download.docker.com` | Docker CE |
  | `github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com` | cosign |
  | `ghcr.io`, `pkg-containers.githubusercontent.com` | образ сайта, cAdvisor |
  | `registry-1.docker.io`, `production.cloudflare.docker.com` | Caddy, Prometheus и другие образы |
  | `tuf-repo-cdn.sigstore.dev`, `rekor.sigstore.dev`, `fulcio.sigstore.dev` | проверка подписи образа |
  | адреса VPN-сервиса (пакеты и вход) | VPN |
  | `ntfy.sh`, адрес внешнего «будильника» | уведомления |

  Проверить всё сразу (на новом сервере, после установки Debian):

  ```bash
  for u in https://deb.debian.org https://download.docker.com \
      https://github.com https://release-assets.githubusercontent.com \
      https://ghcr.io/v2/ https://registry-1.docker.io/v2/ \
      https://tuf-repo-cdn.sigstore.dev https://rekor.sigstore.dev \
      https://ntfy.sh; do
    printf '%-46s ' "$u"
    curl -sS -o /dev/null --max-time 20 -w '%{http_code}\n' "$u" 2>&1 | tail -1
  done
  ```

  Любой код ответа (200, 301, 401, 404) — нормально. Плохо — `000` или ошибка соединения.

## 3. Установка Debian

1. Образ `debian-13.*-amd64-netinst.iso` с [debian.org](https://www.debian.org/distrib/netinst),
   проверить по `SHA256SUMS`.
2. В установщике:
   - **hostname — прежнее имя сервера** (по нему узел называется в VPN и в метриках);
   - **пароль root оставить пустым** — тогда установщик сам добавит пользователя в группу `sudo`;
   - пользователь — тот же логин, что был (его ждёт `~/.ssh/config` управляющей машины);
   - в «Выборе программного обеспечения» — **только «SSH server» и «стандартные системные утилиты»**,
     рабочий стол снять (с GNOME ставится NetworkManager, и система будет отличаться от описанной).
3. Сетевой адрес — тот же, что был (статический или резервирование DHCP в роутере): на нём держатся
   записи DNS для `*.home.arpa`.

## 4. Доступ по SSH

С управляющей машины. Ключ хоста у новой системы другой, поэтому старую запись нужно удалить,
иначе SSH откажется подключаться («REMOTE HOST IDENTIFICATION HAS CHANGED»):

```bash
ssh-keygen -R АДРЕС-СЕРВЕРА
ssh-copy-id ЛОГИН@АДРЕС-СЕРВЕРА
ssh АДРЕС-СЕРВЕРА "groups; systemctl is-active ssh"   # в группах есть sudo, ssh — active
```

Алиас из инвентаря (`homelab`) в `~/.ssh/config` указывает на имя сервера в VPN; пока VPN не настроен
(шаг 5), его можно временно направить на адрес в домашней сети.

## 5. VPN

Плейбук VPN не настраивает. Служебные сайты (Prometheus, Alertmanager, Grafana) открыты только адресам
VPN, поэтому без этого шага они будут отвечать 403. Конкретные команды — в приватных заметках владельца;
здесь — что нужно получить.

1. **В панели управления VPN удалить старый узел сервера** — иначе новый узел получит имя с суффиксом,
   и SSH-алиас перестанет работать.
2. **Установить VPN-клиент из официального репозитория пакетов и подключить сервер** к сети VPN под
   прежним именем.
3. **Вернуть узлу прежний адрес в VPN** (в панели управления). На этом адресе держатся записи DNS для
   служебных сайтов и DNS-сервер для домена `home.arpa` в настройках VPN; если адрес не вернуть —
   поменять их на новый (шаг 7).
4. **Отключить подмену адреса источника для пересылаемого трафика** (SNAT). Иначе VPN-клиент подменяет
   адрес клиента на адрес шлюза Docker, прокси видит не адрес из VPN и отвечает 403 всем. Проверить
   в настройках клиента, что SNAT выключен, а сервер не раздаёт подсети (одобрять маршруты не нужно).

## 6. Плейбук

На управляющей машине, из клона репозитория. `-K` спросит пароль `sudo` на сервере, затем — пароль
файла с секретами:

```bash
cd ansible
ansible-playbook playbook.yml -K \
  -e @$HOME/.config/air-gis/vault.yml --ask-vault-pass
```

- Первый прогон на чистой системе — около 30–40 минут, почти всё время уходит на загрузки. На задаче
  firewall SSH-соединение переподключается: если после применения правил сервер не отвечает, правила
  снимаются сами через 3 минуты.
- В конце роль `monitoring` ждёт, пока все цели Prometheus станут доступны, — `FAILED - RETRYING`
  в этой задаче нормально.
- Загрузки (cosign, ключ репозитория Docker) повторяются до 4 раз: короткий обрыв сети прогон не роняет.
  Упавший прогон можно просто запустить снова — уже сделанное он не повторяет.
- **Второй прогон должен дать `changed=0`.**

Если GitHub с линии сервера недоступен, cosign можно положить вручную — роль сверит контрольную сумму
и скачивать не станет. Версия и сумма — в [`roles/app/defaults/main.yml`](../ansible/roles/app/defaults/main.yml):

```bash
v=v3.1.4
curl -fLO https://github.com/sigstore/cosign/releases/download/$v/cosign-linux-amd64
scp cosign-linux-amd64 АДРЕС-СЕРВЕРА:/tmp/
ssh -t АДРЕС-СЕРВЕРА "sudo install -m 0755 /tmp/cosign-linux-amd64 /usr/local/bin/cosign"
```

## 7. Что вне плейбука

- **DNS домашней сети** — записи для `*.home.arpa`: сайт ведёт на адрес сервера в домашней сети,
  служебные сайты (`prometheus`, `alertmanager`, `grafana`) — на адрес сервера в VPN (иначе клиент
  придёт из домашней сети и получит 403). В VPN — Split DNS для домена `home.arpa`. Если адреса
  сохранились (шаги 3 и 5), менять ничего не нужно.
- **Другие сервисы на сервере**, не описанные в этом репозитории, — из приватного репозитория владельца.

## 8. Проверки

С управляющей машины:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://air-gis.home.arpa/healthz   # 200, без -k
bash ../scripts/smoke_test.sh https://air-gis.home.arpa                        # «Smoke-тест пройден»
```

`curl` без `-k` и без предупреждений — значит, корень центра сертификации тот же и устройства доверяют
новому серверу.

Служебные сайты из VPN — 200, из домашней сети — 403:

```bash
for h in prometheus.home.arpa/-/healthy alertmanager.home.arpa/-/healthy grafana.home.arpa/api/health; do
  printf '%-36s ' "$h"; curl -sS -o /dev/null --max-time 15 -w '%{http_code}\n' "https://$h"
done
```

Состояние мониторинга (на сервере; пользователь не в группе `docker`, поэтому `sudo`):

```bash
q() { sudo docker compose -f /opt/monitoring/compose.yaml exec -T prometheus \
  promtool query instant http://127.0.0.1:9090 "$1" </dev/null; }
q 'ALERTS{alertstate="firing"}'                                  # только Watchdog
q 'count(up == 1)'                                               # 10
q 'sum by (integration) (alertmanager_notifications_total) > 0'  # webhook — уведомления уходят
q 'sum by (integration, reason) (alertmanager_notifications_failed_total) > 0'  # пусто
```

Настоящий алерт:

```bash
sudo docker stop air-gis-web-1    # в течение 2 минут — «🚨 SiteDown» в ntfy
sudo docker start air-gis-web-1   # ещё через пару минут — «✅ Исправлено: SiteDown»
```

Внешний «будильник» через 5–10 минут после запуска показывает, что сигналы снова приходят.

Перезагрузка — сервер поднимается сам (автообновления ночью перезагружают его после обновления ядра):

```bash
sudo reboot
# через 2–3 минуты, на сервере:
sudo docker ps -a --format '{{.Names}} {{.Status}}'   # все Up, ни одного Exited
```

Повторный прогон плейбука проверяет то же без перезагрузки: роль monitoring в конце убеждается, что
ни один её контейнер не помечен как «остановленный вручную» (см. «Подводные камни»).

## Как проверялось

Сценарий прогнан 18–19.11.2026 на чистой ВМ в UTM (эмуляция x86_64 на Mac с Apple Silicon:
нативная ARM-ВМ не подходит — образы только для amd64). Для стенда — отдельный инвентарь
[`inventory/restore-test.yml`](../ansible/inventory/restore-test.yml) и отдельный файл с секретами:
свой канал ntfy и свой адрес «будильника», чтобы стенд не писал в рабочие каналы и не подменял
собою сигналы настоящего сервера. Корень центра сертификации — настоящий: только так проверяется,
что устройства доверяют восстановленному серверу. После теста ВМ удаляется вместе с диском.

| Проверка | Результат |
|---|---|
| Первый прогон на чистом Debian | `failed=0` |
| Повторный прогон | `changed=0` |
| HTTPS без `-k` с управляющей машины | 200 — корень из файла с секретами работает |
| Smoke-тест сайта | пройден |
| Цели Prometheus / горящие алерты | 10 из 10 / только `Watchdog` |
| Уведомления | отправлены, ошибок 0 |
| `SiteDown` (остановка контейнера сайта) | «🚨 SiteDown» и «✅ Исправлено» пришли в тестовый канал |
| Служебные сайты: из VPN / из домашней сети | 200 / 403 |
| То же с включённой подменой адреса (SNAT) | из VPN 403 — шаг 5.4 обязателен |

Что нашёл прогон и что исправлено:

- У `get_url` по умолчанию таймаут 10 секунд и нет повторов, а TLS-рукопожатие с некоторыми адресами
  на домашней линии занимало до 16 секунд → у загрузок cosign и ключа Docker таймаут 60 секунд
  и 4 повтора.
- Корень центра сертификации раньше жил только в томе Docker: при восстановлении появился бы новый,
  и корневой сертификат пришлось бы ставить на все устройства заново → корень перенесён в файл
  с секретами.

Что **не** проверено на стенде (нельзя без вмешательства в рабочий VPN): удаление старого узла
и возврат прежнего адреса в VPN (шаг 5, пункты 1 и 3).

## Подводные камни

- **Корпоративная сеть может резать загрузки с GitHub** (обрыв TLS-рукопожатия) — проверка адресов
  из раздела 2 покажет это до запуска плейбука.
- **Служебные сайты из VPN: TCP-соединение открывается, но HTTPS висит** — на клиенте мешает другой
  VPN-клиент (большие пакеты не проходят через двойной туннель). На стенде помогло выключить его.
- **`ssh -t host "sudo cmd; rm -f файл"`** удалит файл, даже если пароль `sudo` не подошёл, — писать `&&`.
- Пароль при `-K` вводится вслепую; «Incorrect sudo password» на первом шаге — опечатка, запустить снова.
- **Контейнер не поднялся после перезагрузки, хотя у него `restart: unless-stopped`** — ему когда-то
  послали сигнал через API Docker (`docker kill`, `docker compose kill`, даже SIGHUP для перечитывания
  конфигурации): Docker считает такой контейнер остановленным вручную. Сигналы для перечитывания
  роль посылает изнутри контейнера (`docker compose exec … kill -HUP 1`). Вручную тоже только так.
  Найдено 25.11.2026: после ночной перезагрузки не запустились Prometheus и blackbox_exporter, тревогу
  поднял внешний «будильник».
